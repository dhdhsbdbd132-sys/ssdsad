# Безопасность и развёртывание

## Пароли, 2FA и сессии

Пароли хешируются Argon2id. Почтовый код — 6 случайных цифр, 10 минут, 5 попыток, одноразовый; хранится HMAC, а не открытый код. Новый challenge аннулирует предыдущий. JWT живёт 15 минут и проверяется по алгоритму, сроку, issuer/audience и действующей серверной сессии. Роли извлекаются из БД при каждом запросе; поле role в JWT не используется.

Refresh-токен случайный, живёт 7 дней; в БД только SHA-256. Каждое обновление выдаёт новый токен. Повторное использование старого отзывает семейство сессии. Выход и назначение роли отзывают сессии немедленно. Клиент хранит токены в памяти, а не в JSON-файле или обычном Android storage.

Запросы выполняются в одном рабочем потоке клиента, что предотвращает одновременную ротацию одного refresh-токена. На сервере optimistic locking защищает от гонок.

## Настройка настоящей почты

Создайте `.env` по образцу `.env.example`. Установите `MAIL_BACKEND=smtp`, `SMTP_HOST`, `SMTP_PORT=587`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_SENDER`. Используется STARTTLS с проверкой сертификата. Пароль передаётся через защищённую конфигурацию процесса, не через чат и не через репозиторий. SMTP должен быть доступен серверу. Локальный файловый mailbox намеренно запрещён в production.

## Google OAuth / OIDC

В Google Cloud создайте OAuth client типа **Web application** для серверной стороны. Укажите точный redirect URI (в development `http://localhost:8000/api/auth/oauth/callback`, в production HTTPS-адрес вашего API). Consent screen должен разрешать нужных пользователей.

Настройте `OAUTH_CLIENT_ID`, `OAUTH_CLIENT_SECRET`, `OAUTH_REDIRECT_URI`. Discovery/issuer по умолчанию Google. Сервер выполняет Authorization Code + PKCE S256, проверяет одноразовый state, nonce, RS256 через JWKS, issuer, audience, expiry и `email_verified=true`. Ключ провайдера не принимается из самого ID token.

Android-клиент открывает системный браузер, а результат получает по защищённому одноразовому poll-key. В callback или URL нет access/refresh-токенов. Пользователь возвращается в Kivy и вводит почтовый код. При совпадении адреса с существующей учётной записью доступ также требует свежего кода на этот адрес. Без подтверждённой почты вход невозможен.

Нужны HTTPS-соединения к `accounts.google.com`, `oauth2.googleapis.com` и адресу JWKS из официального discovery Google (обычно `www.googleapis.com`). Для карт — `a.basemaps.cartocdn.com`. Сетевая доступность и разрешение провайдера проверяются отдельно после настройки credentials.

## Инфраструктура

`deploy/Dockerfile` запускает API как UID 10001. `deploy/compose.yml`:

- PostgreSQL не публикует порт наружу, данные сохраняются в отдельном volume.
- API слушает опубликованный порт только на loopback хоста для HTTPS-прокси.
- Файловая система API read-only, временные файлы в tmpfs.
- Удалены Linux capabilities, запрещено повышение привилегий.
- Ограничены память и число процессов, настроено ожидание здоровья БД.

`deploy/nginx.conf` — пример внешнего HTTPS-прокси: TLS 1.2/1.3, HSTS, ограничения размеров и запросов по IP, скрытая версия сервера. Нужны реальные DNS и сертификаты. Конфигурация не является автоматическим развёртыванием: Nginx не запускается самим compose-файлом.

Сервер дополнительно использует allowed hosts, HTTP security headers, лимит авторизации, не раскрывает внутренние исключения и не пишет тела запросов или bearer-токены в access logs. В Docker отключено доверие к forwarded headers. Поэтому внутренний лимит API за reverse proxy может считать общий адрес прокси; для этого режима настройте `RATE_LIMIT=1000`, а внешний Nginx оставьте ответственным за индивидуальный лимит. При нескольких API-инстансах необходим общий limiter (например, Redis); текущий in-memory limiter рассчитан на один экземпляр.

## Запуск production

Создайте `.env` с `ENVIRONMENT=production`, `SECRET_KEY` (минимум 32 случайных символа), SMTP, `OAUTH_REDIRECT_URI=https://...` и `ALLOWED_HOSTS=api.example.com`. Для PostgreSQL задайте безопасный случайный URL-compatible пароль `POSTGRES_PASSWORD` в защищённом окружении или отдельном закрытом env-файле. Не используйте одинаковые пароли между окружениями.

```bash
docker compose --env-file .env -f deploy/compose.yml up -d --build
```

Секреты не передавайте через публичные команды/логи. Сервер отклоняет production с SQLite, отсутствующим ключом, файловой почтой, wildcard-hosts или HTTP OAuth callback. Миграции применяются при старте; создайте администратора отдельной CLI-командой внутри API-контейнера. Перед обновлением делайте резервную копию PostgreSQL.

Периодически очищайте просроченные auth-записи: `python -m app.cli clean-auth` с `PYTHONPATH=backend`. До срока истечения использованные refresh-записи сохраняются для обнаружения replay. Аудит остаётся в БД; политика долговременного хранения определяется владельцем сервиса.

Эти меры реализованы в коде и конфигурации. Развёртывание на публичном сервере, реальные TLS-сертификаты, доставка SMTP, внешняя Google-интеграция и нагрузочный/инфраструктурный аудит требуют отдельной проверки в целевом окружении.
