# Безопасность и развёртывание

## Пароли, 2FA и сессии

Пароли хешируются Argon2id. Почтовый код — 6 случайных цифр, 10 минут, 5 попыток, одноразовый; хранится HMAC, а не открытый код. Новый challenge аннулирует предыдущий. JWT живёт 15 минут и проверяется по алгоритму, сроку, issuer/audience и действующей серверной сессии. Роли извлекаются из БД при каждом запросе; поле role в JWT не используется.

Refresh-токен случайный, живёт 7 дней; в БД только SHA-256. Каждое обновление выдаёт новый токен. Повторное использование старого отзывает семейство сессии. Выход и назначение роли отзывают сессии немедленно. Клиент хранит токены в памяти, а не в JSON-файле или обычном Android storage.

Запросы выполняются в одном рабочем потоке клиента, что предотвращает одновременную ротацию одного refresh-токена. На сервере optimistic locking защищает от гонок.

## Настройка настоящей почты

На Windows запустите `CONFIGURE_EMAIL_WINDOWS.bat`. Для Mail.ru мастер использует `smtp.mail.ru`, порт 465 и SSL/TLS с проверкой сертификата. Введите полный адрес отправителя и пароль из Mail.ru → Настройки → Все настройки → Безопасность → Пароли для внешних приложений. Ввод скрыт; пароль сохраняется только в игнорируемом `.env`. По явному выбору можно отправить проверочное письмо; при ошибке прежняя конфигурация сохраняется. После настройки перезапустите сервер.

Вручную: `MAIL_BACKEND=smtp`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURITY`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_SENDER`. Для 465 используйте `SMTP_SECURITY=ssl`; для 587 — `starttls`. Незащищённый SMTP не поддерживается. Адрес отправителя должен быть разрешён вашим почтовым сервисом. Резервная копия прежнего `.env` находится в `.data/email-settings-backups` и также содержит секреты: не публикуйте её. На POSIX файлы имеют права 0600; на Windows наследуют права пользовательской папки.

В development без SMTP используется локальный mailbox. API честно возвращает `delivery=development_file`, а сам код остаётся только в локальном письме. В production файловый режим запрещён. Сбой отправки возвращает безопасную ошибку 503, без паролей или полного ответа SMTP; регистрация и обновление challenge откатываются.

## Вход и сеть

Google-вход удалён из клиента, API и конфигурации. OAuth2 `/auth/token` сохраняет совместимость со Swagger и требует тот же почтовый код; обхода 2FA нет.

Публичный API требует HTTPS. Для локального подключения APK к своему ПК разрешён HTTP только к конкретному IPv4-адресу из сетей 10/8, 172.16/12 или 192.168/16, когда пользователь включил режим ПК через Wi-Fi. Публичные IP, произвольные HTTP-домены и адрес 0.0.0.0 клиент отклоняет. Это режим разработки в своей локальной сети; production использует HTTPS. `START_ANDROID_SERVER_WINDOWS.bat` публикует development API для LAN, сохраняет явный список allowed hosts и не меняет брандмауэр автоматически.

Для карт нужны HTTPS-соединения к `tile.openstreetmap.org` и резервному `a.tile.openstreetmap.fr`; картографические API-ключи не нужны. Проверка TLS остаётся включённой, повреждённые изображения не сохраняются, тайлы кэшируются локально.

## Инфраструктура

`deploy/Dockerfile` запускает API как UID 10001. `deploy/compose.yml`:

- PostgreSQL не публикует порт наружу, данные сохраняются в отдельном volume.
- API слушает опубликованный порт только на loopback хоста для HTTPS-прокси.
- Файловая система API read-only, временные файлы в tmpfs.
- Удалены Linux capabilities, запрещено повышение привилегий.
- Ограничены память и число процессов, настроено ожидание здоровья БД.

`deploy/nginx.conf` — пример внешнего HTTPS-прокси: TLS 1.2/1.3, HSTS, ограничения размеров и запросов по IP, скрытая версия сервера. Нужны реальные DNS и сертификаты. Конфигурация не является автоматическим развёртыванием: Nginx не запускается самим compose-файлом.

Сервер дополнительно использует allowed hosts, HTTP security headers, лимит авторизации, не раскрывает внутренние исключения и не пишет тела запросов или bearer-токены в access logs. В Docker отключено доверие к forwarded headers. Поэтому внутренний лимит API за reverse proxy может считать общий адрес прокси; для этого режима настройте `RATE_LIMIT=1000`, а внешний Nginx оставьте ответственным за индивидуальный лимит. При нескольких API-инстансах необходим общий limiter (например, Redis); текущий in-memory limiter рассчитан на один экземпляр.

## Запуск production

Создайте `.env` с `ENVIRONMENT=production`, `SECRET_KEY` (минимум 32 случайных символа), SMTP и `ALLOWED_HOSTS=api.example.com`. Для PostgreSQL задайте безопасный случайный URL-compatible пароль `POSTGRES_PASSWORD` в защищённом окружении или отдельном закрытом env-файле. Не используйте одинаковые пароли между окружениями.

```bash
docker compose --env-file .env -f deploy/compose.yml up -d --build
```

Секреты не передавайте через публичные команды/логи. Сервер отклоняет production с SQLite, отсутствующим ключом, файловой почтой или wildcard-hosts. Миграции применяются при старте; создайте администратора отдельной CLI-командой внутри API-контейнера. Перед обновлением делайте резервную копию PostgreSQL.

Периодически очищайте просроченные auth-записи: `python -m app.cli clean-auth` с `PYTHONPATH=backend`. До срока истечения использованные refresh-записи сохраняются для обнаружения replay. Аудит остаётся в БД; политика долговременного хранения определяется владельцем сервиса.

Эти меры реализованы в коде и конфигурации. Развёртывание на публичном сервере, реальные TLS-сертификаты, доставка SMTP с учётными данными и нагрузочный/инфраструктурный аудит требуют отдельной проверки в целевом окружении.
